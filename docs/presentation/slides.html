Business Problem & Requirements
The Core Banking Conundrum: Real-Time vs ACID Consistency
1. Network Retries & Replays
  • The Risk: Unreliable mobile networks cause clients to aggressively retry fund transfers.
  • The Catastrophe: Without deterministic idempotency, network retries trigger duplicate debit deductions.
  • IndiBank Solution: Redis SETNX with 24-hour cached receipt returns the exact settled response without re-debiting.
2. Concurrency & Race Conditions
  • The Risk: Concurrent API requests draining the same account simultaneously (payroll runs, automated sweeps).
  • The Catastrophe: Read-modify-write race conditions lead to negative balances and overdrafts.
  • IndiBank Solution: Distributed mutex with 10s auto-expiry and atomic Lua verification guarantees single-flight execution.
3. Ledger Drift & Auditability
  • The Risk: In-place balance mutations lose historical context and violate financial audit regulations.
  • The Catastrophe: Money appears or vanishes without an offsetting journal entry, failing banking audit.
  • IndiBank Solution: Strict Double-Entry Bookkeeping in Oracle 23c ensures total debits always equal total credits.

Financial Consistency & Safety
Defensive Concurrency & Zero-Loss Ledger Guarantees
1. Redis Idempotency State Machine
  • Atomic Key Acquisition: SETNX indibank:idempotency:{key} IN_PROGRESS with 60s lock window.
  • In-Flight Deduplication: Concurrent requests with the same key receive HTTP 409 Conflict immediately.
  • 24-Hour Replay Cache: On settlement, complete response payload is cached for 86,400s.
  • Safe Retries: Key is released on business validation error to allow corrected submissions.
2. Distributed Mutex & Lua Release
  • Source Account Lock: SET indibank:lock:account:{acc} {UUID} NX PX 10000 ensures single-flight execution.
  • Auto-Expiry TTL: 10-second TTL prevents deadlocks if a container crashes mid-transaction.
  • Atomic Lua Release: Validates token ownership before deleting, preventing lock hijacking.
  • Graceful Contention: Lock failure returns 409 Conflict with retry suggestion.
3. Strict Double-Entry Bookkeeping
  • Mathematical Balance: Every transfer produces matching DEBIT and CREDIT journal lines.
  • Zero Ledger Drift: Invariance guaranteed: |Debit - Credit| == 0.00 IDR across all transactions.
  • Immutable Ledger: Journal entries are append-only; historical entries are never updated or deleted.
  • Audit Statement API: Real-time historical statement query via /api/v1/accounts/{acc}/statement.
4. Database Constraints & Optimistic Locking
  • Non-Negative Balance: Oracle CHECK constraint (BALANCE >= 0) physically prevents overdrafts.
  • Optimistic Locking: @Version column on ACCOUNTS prevents concurrent dirty updates.
  • Atomic Rollback: Spring @Transactional rolls back debit/credit and releases locks on failure.
  • Transactional Outbox: Guarantees event dispatch consistency with database ledger state.
Event Streaming & Compliance
Apache Kafka KRaft: Asynchronous Decoupling & Real-Time AML
Kafka KRaft Event Architecture
  • Zookeeper-Less Architecture: Apache Kafka 3.7+ running in KRaft mode for lower latency, faster leader election, and lightweight operations.
  • Topic 1: bank.transfers.settled: Emitted immediately after Oracle ACID commit. Payload contains full transfer details, accounts, amount, and timestamp.
  • Topic 2: bank.fraud.alerts: Emitted by real-time AML worker whenever high-risk transactions are detected.
  • Topic 3: bank.transfers.dlq: Dead-letter queue capturing failed messages after 3 retries with exponential backoff.
  • Async Decoupling: User receives 201 Created immediately; heavy notifications and compliance analytics process asynchronously.
Real-Time AML Compliance Engine
  • High-Value Detection Rule: Automatically flags any single transfer >= Rp 100,000,000 as CRITICAL AML risk.
  • Independent Consumer Group: Consumer group 'indibank-fraud-detector' processes settled events in parallel without latency impact on transfers.
  • Compliance Alert Payload: Emits structured alert events with severity, reason, and compliance reference.
  • In-Memory Live Stream Ticker: RecentEventsTracker maintains an in-memory ring buffer exposed at /api/v1/events/recent.
  • Interactive Demonstration: Evaluators can watch Kafka events stream in real-time on our interactive banking dashboard.

Standardized RFC 7807 Errors
  • RFC 7807 Problem Details: All error responses conform to the standard banking error contract (ApiErrorDto).
  • HTTP 400 Bad Request: Missing headers, invalid 10-digit account formatting, or payload schema violations.
  • HTTP 409 Conflict: Duplicate transfer in-flight or distributed account lock contention.
  • HTTP 422 Unprocessable: Domain rule violations: insufficient funds, inactive accounts, or negative amounts.

Site Reliability Engineering
Production SRE Framework, SLOs, & Real-Time Telemetry
SLOs & Error Budgets
  • Availability SLO: >= 99.99% (Four Nines) on a rolling 30-day window (4.32 min/month error budget).
  • Latency SLO (p95): <= 150 ms end-to-end settlement latency.
  • Latency SLO (p99): <= 500 ms worst-case latency including distributed locking and Kafka publish.
  • Ledger Invariance SLO: Zero mathematical drift (|Debit - Credit| == 0.00 IDR) with ZERO error tolerance.
  • Multi-Burn Alerting: 1-hour burn rate >= 14.4x triggers P1 pager alert; deployment freeze if budget drops < 10%.
Four Golden Signals
  • Latency: Percentile histograms (p50, p95, p99) tracked per endpoint and channel via Micrometer.
  • Traffic: Real-time RPS and throughput counters partitioned by currency and status.
  • Errors: Distinguishes 4xx business validations (which don't burn budget) from 5xx server faults.
  • Saturation: HikariCP Oracle pool pending threads, Kafka consumer group lag, and ZGC heap memory.
  • Live Endpoint: Exposed live at /actuator/prometheus for automated scraping.
Alerting & Autoscaling
  • Prometheus Alert Rules: monitoring/prometheus-alerts.yaml defines production alerts for 5xx errors, latency, and pool starvation.
  • Oracle Pool Starvation: Alerts when hikaricp_connections_pending > 0 for > 30s.
  • Kafka Consumer Lag: Alerts when fraud consumer lag exceeds 500 messages.
  • Kubernetes HPA: k8s/hpa.yaml scales replicas from 1 to 5 based on 70% CPU and 80% Memory utilization.
  • Incident SOP Runbooks: Standard Operating Procedures (SOP-01 to SOP-03) documented for on-call SREs.
